# Continue here

The user wants to experience shipping an independently branded app into the Zepp OS store. This is the new repository; Basket Birdie continues separately.

## Agreed direction

- Standalone repo/product, not a feature of the larger disc-golf app.
- General repetition/practice tracking, not restricted to golf.
- Flexible measure: longer distances, duration, weight and extensible/custom units.
- Preserve the mockup-inspired green value card, distinct outcome cards and make-rate bar as the visual starting point.
- Target as many Zepp OS watches as practical, not only Amazfit Bip Max. Bip Max is the current build/simulator target and pictured device; additional watch compatibility must be implemented and verified before being claimed.

## Product decisions and open inputs

- Tallyform is the current working name; publisher registration and store availability are unverified.
- The approved release change implements both simple repetitions and success/failure attempts, with one fixed measurement type per session. Custom numeric settings are not implemented.
- Duration is a selected practice value, **not** a stopwatch or countdown. Native timer controls and background integration remain gated.
- Store regions, pricing, publisher details and registered app ID remain unresolved.

## Versioned native persistence and generic UI

The v2 pure session domain fixes mode/type at start, records immutable canonical values, computes selected versus whole-session totals and rejects a 1001st event while retaining the first 1000. The Bip Max page uses touch controls for both modes and four measurement types. Imported legacy key mappings remain usable; new-session device-specific hardware mapping is not yet implemented. The pure timer domain is not connected to this UI.

`app/page/repository.js` writes active v2 and history-summary v1 as independent immutable generations, verifies each generation and alternating pointer before reporting success, retains both referenced generations during normal cleanup and refuses writes on torn/unknown data. A committed null active record is the durable migration tombstone. History is capped at **100 summaries**, each summary at **1000 events**; full capacity blocks a new finish rather than silently evicting. Deletion is confirmed. Finish commits the stable-ID summary before clearing active state; after an interrupted clear, the page freezes recording and resumes cleanup without duplicating the summary. An active corruption can still expose intact history, and history corruption blocks finish without discarding the active record. No automatic reset or destructive recovery occurs.

`putting-session-v1` is read only while no v2 active commit exists, validated, mapped to outcome/distance with exactly ordered metres/feet event values, outcome flags and usable imported keys, and committed to the v2 active slot. Unknown legacy start/stopwatch times are `null`; the original snapshot is never modified or deleted. After finish/discard, the committed null marker prevents reimport. This migration only sees data when the app **keeps the same ID and storage identity**; inherited ID `1126719` is not a registered product ID. Preserve development data and verify an actual same-ID upgrade before any publisher-ID switch; no cross-ID migration or copy has been performed.

## Pure timer model (not yet alarm integration)

`app/page/timers.js` now implements injected-clock stopwatch and countdown transitions with independent state: pause/resume, explicit restart/cancel, duration snapshot, expiry recovery and terminal stopwatch time. A clock sample must supply wall milliseconds, boot-scoped monotonic milliseconds and a stable boot ID. The model uses monotonic elapsed time while wall/monotonic drift within 5 seconds is consistent; backward time, larger drift or a different boot marks timing **uncertain** without inventing elapsed time. Explicit resume retains that uncertainty; restart clears it. A native adapter must verify the actual clock/boot sources and persist controls before this behavior is available on a watch.

`node --test tests/timers.test.js` passed 6/6; the full `npm test` passed **55/55**, `npm run build` succeeded, and a fresh-process smoke observed 25,000 ms stopwatch elapsed with an independently expired countdown at 0 ms remaining. These are host/domain and prototype packaging checks, **not** evidence that the current watch app offers a timer or that background alerts work. Task 4.1 is complete as a pure state-machine task; tasks 4.2–4.5 remain gated by the unresolved physical shared-state/alarm qualification.
